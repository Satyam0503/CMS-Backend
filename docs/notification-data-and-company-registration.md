# Notifications: storage, delivery and company-registration impact

This document explains where notification data is stored (MongoDB collections), how notifications are created and delivered (persistence + real-time SignalR), and what happens during a new company registration that affects notification data and preferences.

## 1. Data model (MongoDB collections)

The application stores notification-related data in MongoDB collections. Key collections and their purpose:

- `Notifications` (entity class: `Notifications`)
  - Purpose: a company-scoped notification message/document (the canonical notification content).
  - Important fields:
    - `NotificationId` (primary id, generated by UniqueIdGenerator)
    - `Title` and `Body` (display text)
    - `TargetId` (optional reference, e.g., NoticeId, LeaveRequestId)
    - `NotificationType` (enum; e.g., Notice, LeaveRequest)
    - `CreatedDateTime`, `CreatedBy`
    - `CompanyId` (tenant isolation) — services should set this when creating company-scoped notifications.
  - File: [Codeji.CMS.Repository/Entities/Notification.cs](Codeji.CMS.Repository/Entities/Notification.cs#L1-L40)

- `UserNotifications` (entity class: `UserNotifications`)
  - Purpose: per-recipient durable inbox entries. Each record links a `UserId` to a `NotificationId` and records read/delete state.
  - Important fields:
    - `UserNotificationId` (primary id)
    - `UserId` (recipient)
    - `NotificationId` (reference to Notifications.NotificationId)
    - `IsRead`, `IsDeleted`, `CreatedDateTime`
  - File: [Codeji.CMS.Repository/Entities/UserNotifications.cs](Codeji.CMS.Repository/Entities/UserNotifications.cs#L1-L40)

- `NotificationPreference` (entity class: `NotificationPreference`)
  - Purpose: per-user preference map (which types of notifications the user opts in/out for).
  - Implemented as a dictionary of `NotificationPreferenceType -> bool`.
  - File: [Codeji.CMS.Repository/Entities/NotificationPreference.cs](Codeji.CMS.Repository/Entities/NotificationPreference.cs#L1-L80)

- `EmpEmailLogs` (not covered in detail here) is used to persist emails sent as part of notifications and onboarding (see `MiddlewareService.EmailSendAndSave`). See references in the docs and codebase.

Notes: all repository entities are persisted using the in-project `IMongoDbRepository<T>` abstractions which apply default filters for `CompanyId` and soft-delete behavior unless bypassed explicitly.

## 2. Typical creation & delivery flow (example: posting a notice)

The canonical flow used by services (NoticeBoard, Leave, Employee events) is:

1. Service creates a domain-specific entity (e.g., a `Notice` or `LeaveRequest`) and persists it.
2. Service creates a `Notifications` document containing title/body/target/type and sets `CreatedDateTime` and `CompanyId`.
   - Example: `NotificationTitle = NotificationMessageTemplate.Create(NotificationTypes.Notice)`.
   - File: `NoticeBoardServices.PostNotice` shows this pattern: it builds `Notifications` then calls `_notificationRepository.AddOne(notification)`.
   - File: [Codeji.CMS.Services/NoticeBoard/NoticeBoardServices.cs](Codeji.CMS.Services/NoticeBoard/NoticeBoardServices.cs#L1-L260)

3. Service determines recipients (e.g., all employees in certain department or a single user). The recipient selection usually respects:
   - Company scoping (only users with `CompanyId` matching the current tenant)
   - User preferences (via `MiddlewareService.IsUserNotificationPreferenceEnabled(userId, prefType)`)

4. For each recipient, service creates a `UserNotifications` entry and collects an in-memory list of those entries.
   - The `UserNotifications` record links `UserId` to `NotificationId` and sets `IsRead = false`.

5. Real-time delivery: the service uses the `INotificationService` (API-layer wrapper around SignalR `IHubContext<NotificationHub>`) to push a `NotificationViewModel` to the recipient(s).
   - `NotificationService.SendNotificationToUser(userId, NotificationViewModel)` calls `hubContext.Clients.User(userId).SendAsync("notification", model)`.
   - The NotificationHub uses authentication and groups users by `company_{companyId}` to support company-wide broadcasts and to validate company context on connect. See [Codeji.CMS.API/Notification/NotificationHub.cs](Codeji.CMS.API/Notification/NotificationHub.cs#L1-L200).

6. Persistence: after queuing/sending SignalR events, the service writes the batch of `UserNotifications` to Mongo (e.g., `AddMany(userNotifications)`). This ensures durable delivery for offline users.

7. Optional: send emails via `MiddlewareService.EmailSendAndSave` (which writes `EmpEmailLogs` and delegates to the configured SMTP/email provider) if the notification type requires email.

8. Frontend: connected clients subscribe to SignalR `NotificationHub` and listen for `notification` events (client code lives in `CMS-React` under `src/server/SignalR.tsx` and `src/_themes/...` UI components). On receiving a push, UI typically shows a toast and prepends the notification to the in-memory list, while the persisted `UserNotifications` ensures the list is available when the user reloads.

## 3. SignalR specifics and group scoping

- `NotificationHub.OnConnectedAsync` inspects the current HTTP request context to determine `CompanyId`. If no `CompanyId` is present, the connection is rejected. When present the connection is added to group `company_{companyId}`. This allows services to broadcast to all users in a company by sending to that group.
  - File: [Codeji.CMS.API/Notification/NotificationHub.cs](Codeji.CMS.API/Notification/NotificationHub.cs#L1-L200)

- `NotificationService` (API) exposes `SendNotificationToUser(userId, model)` that calls `hubContext.Clients.User(userId).SendAsync("notification", model)` — this sends a user-targeted message (not group).
  - File: [Codeji.CMS.API/Notification/NotificationService.cs](Codeji.CMS.API/Notification/NotificationService.cs#L1-L200)

- Important: SignalR delivery is a supplementary real-time layer. The durable record is the `UserNotifications` document — services write it so offline/slow clients can still see historical notifications.

## 4. New company registration effects (what the `Register` flow does)

When a new company registers (see `CompanyService.Register`), the following actions directly related to notification behavior occur:

- New `Company` document is created and persisted with `CompanyId`.
  - File: [Codeji.CMS.Services/Companies/CompanyService.cs](Codeji.CMS.Services/Companies/CompanyService.cs#L1-L220)

- A primary admin `EmpUser` account is created for the registering email. That user is persisted with `CompanyId = <new company id>`.

- Default roles are created via `RoleService.AddDefaultRole(companyId)` and assigned — this ensures the application modules and permissions exist for the new tenant.

- A `NotificationPreference` record is created for the admin user using defaults from `MiddlewareService.GetDefaultNotificationPreferences()`.
  - This stores the per-user dictionary of notification preference types (all default to `true` by default) so new users start with a predictable opt-in state.
  - File: [Codeji.CMS.Services/Middleware.cs](Codeji.CMS.Services/Middleware.cs#L1-L220)

- The registration seeds default departments and job titles (idempotent), which are used later when services compute recipient sets for certain notifications (e.g., department-targeted notices).

- The registration sends a verification email and writes an `EmpEmailLogs` record.

Summary: on register, the system does not automatically generate broadcast notifications for all users (there are no global `Notifications` created just for registration), but it DOES create the foundational pieces required for notifications to work correctly for that company: tenant record, admin user, role-permissions, and base `NotificationPreference` for the admin. Once employees are created in the company, services will use the standard flow (create `Notifications` + `UserNotifications` + SignalR/email) to deliver messages.

## 5. Where to look when debugging notification issues

- Is a `Notifications` document created? Check the `Notifications` collection (via Mongo shell or your dev GUI). If missing, the service likely failed before creating the notification content.
  - File: [Codeji.CMS.Repository/Entities/Notification.cs](Codeji.CMS.Repository/Entities/Notification.cs#L1-L40)

- Are `UserNotifications` entries present for recipients? Missing `UserNotifications` means the durable inbox wasn't written — check service logs around the `AddMany` call.
  - Example: `NoticeBoardServices.PostNotice` builds `userNotifications` and does `_userNotificationsRepository.AddMany(userNotifications)`.
  - File: [Codeji.CMS.Services/NoticeBoard/NoticeBoardServices.cs](Codeji.CMS.Services/NoticeBoard/NoticeBoardServices.cs#L1-L260)

- Is SignalR sending events? Check `NotificationService.SendNotificationToUser` usage and the SignalR hub logs. Verify the client successfully connected and has the correct `CompanyId` in context (the hub rejects otherwise).
  - File: [Codeji.CMS.API/Notification/NotificationHub.cs](Codeji.CMS.API/Notification/NotificationHub.cs#L1-L200)

- Are recipient preferences blocking delivery? Check `NotificationPreference` entries for the recipient and the `MiddlewareService.IsUserNotificationPreferenceEnabled` helper which falls back to defaults when a preference row is missing.
  - File: [Codeji.CMS.Services/Middleware.cs](Codeji.CMS.Services/Middleware.cs#L1-L220)

- Email audits: check `EmpEmailLogs` for emails queued/sent.

## 6. Practical examples & code pointers

- Posting a Notice (end-to-end in code):
  - Service persists `Notice` → creates `Notifications` → derives recipients → creates `UserNotifications` items → calls `notificationService.SendNotificationToUser` for each `UserId` → persists `UserNotifications` (AddMany) → (optional) email.
  - Implemented in: [Codeji.CMS.Services/NoticeBoard/NoticeBoardServices.cs](Codeji.CMS.Services/NoticeBoard/NoticeBoardServices.cs#L1-L260)

- Sending single-user notification (e.g., leave approval to employee): similar pattern used in `LeaveManagementService` (create notification, add one `UserNotifications`, call hub service to push to the single user).
  - See: `Codeji.CMS.Services/LeaveManagement/LeaveManagementService.cs` (search for `_notificationRepository` / `UserNotifications`).

- New company registration and notification preference seeding: see `CompanyService.Register`.
  - File: [Codeji.CMS.Services/Companies/CompanyService.cs](Codeji.CMS.Services/Companies/CompanyService.cs#L1-L220)

## 7. Recommended improvements (short list)

- Confirm `Notifications.CompanyId` is always set by services that create company-scoped notifications — a missing CompanyId will break tenant isolation and SignalR grouping expectations.
- Add transaction-like auditing for failures: if SignalR push fails but persistence succeeds, that is usually fine, but if persistence fails after push you may have duplicate toasts. Consider ordering and idempotency strategies.
- Consider adding a short retention/archival policy and index the `UserNotifications` by `UserId` + `CreatedDateTime` for fast inbox queries.
- For large broadcasts (e.g., all employees in a large company), consider batching writes and using a background worker to avoid request-time latency.
